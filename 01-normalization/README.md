# Лабораторная работа №1: Принципы построения реляционных БД и нормализация (3НФ)

**Цель работы:** Спроектировать 3 реляционные базы данных для объектов реального мира, выбрать оптимальные типы данных, определить первичные (`PK`) и внешние (`FK`) ключи и привести схемы к третьей нормальной форме (3НФ).

---

## Пример 1: База данных автосалона (Car Dealership)

База данных описывает продажи автомобилей менеджерами салона. Для соблюдения **3НФ** сущности разделены на три таблицы: данные о менеджере и автомобиле вынесены в отдельные справочники, чтобы избежать дублирования при повторных продажах.

### 1. Таблица `managers` (Менеджеры)
*Первичный ключ:* `id`

| id (PK) | name | surname | phone |
| :--- | :--- | :--- | :--- |
| **1** | Иван | Иванов | +375293467764 |
| **2** | Андрей | Петров | +375296763436 |
| **3** | Виктория | Алданова | +375297564457 |

* **Выбор типов данных:**
  * `id`: `INT AUTO_INCREMENT` — целочисленный уникальный идентификатор.
  * `name`, `surname`: `VARCHAR(50)` — строки переменной длины (экономят память).
  * `phone`: `VARCHAR(20)` — строка (не `INT`, так как телефон может содержать `+`, скобки или начинаться с нуля).

### 2. Таблица `cars` (Автомобили)
*Первичный ключ:* `id`

| id (PK) | car_brand | model | body_type | color |
| :--- | :--- | :--- | :--- | :--- |
| **12** | BMW | M3 | седан | серый |
| **23** | BMW | M5 | седан | черный |
| **34** | Audi | Q7 | внедорожник | белый |

* **Выбор типов данных:**
  * `id`: `INT AUTO_INCREMENT` — первичный ключ.
  * `car_brand`, `model`, `body_type`, `color`: `VARCHAR(50)` — текстовые атрибуты автомобиля.

### 3. Таблица `sales` (Продажи)
*Первичный ключ:* `id` | *Внешние ключи:* `manager_id` -> `managers(id)`, `car_id` -> `cars(id)`

| id (PK) | manager_id (FK) | car_id (FK) | date_of_sale | price |
| :--- | :--- | :--- | :--- | :--- |
| **112** | 1 | 12 | 2023-03-28 | 70000.00 |
| **223** | 2 | 23 | 2023-03-12 | 95000.00 |
| **334** | 3 | 34 | 2023-02-23 | 45000.00 |

* **Выбор типов данных:**
  * `date_of_sale`: `DATE` — специализированный тип для хранения даты в формате `YYYY-MM-DD`.
  * `price`: `DECIMAL(10, 2)` — точный финансовый тип данных (исключает ошибки округления с плавающей точкой).

## Пример 2: База данных университета (University Structure)

Моделирует структуру факультетов, учебных групп и деканов. Приведена к **3НФ**: данные о декане (`s_name`, `s_dob`) вынесены из таблицы групп и факультетов в отдельное отношение `staff`, что устраняет транзитивную зависимость `grp -> faculty -> staff`.

### 1. Таблица `staff` (Преподаватели / Деканы)
*Первичный ключ:* `s_id`

| s_id (PK) | s_name | s_dob |
| :--- | :--- | :--- |
| **1** | John Smith | 1974-01-12 |
| **2** | Joe Black | 1984-12-23 |
| **3** | Jane Dow | 1985-05-28 |

### 2. Таблица `faculty` (Факультеты)
*Первичный ключ:* `f_id` | *Внешний ключ:* `f_dean_id` -> `staff(s_id)`

| f_id (PK) | f_name | f_dean_id (FK) |
| :--- | :--- | :--- |
| **1** | ФКП | 1 |
| **2** | ФИТУ | 2 |
| **3** | ИЭФ | 3 |

### 3. Таблица `grp` (Учебные группы)
*Первичный ключ:* `g_id` | *Внешний ключ:* `g_faculty` -> `faculty(f_id)`

| g_id (PK) | g_num | g_start_year | g_faculty (FK) |
| :--- | :--- | :--- | :--- |
| **1** | 080255 | 2020 | 1 |
| **2** | 080555 | 2020 | 2 |
| **3** | 280355 | 2022 | 3 |

* **Выбор типов данных:**
  * `s_id`, `f_id`, `g_id`: `INT AUTO_INCREMENT` (Первичные ключи).
  * `s_dob`: `DATE` (Дата рождения сотрудника).
  * `g_start_year`: `YEAR` или `SMALLINT` (Год поступления группы).
  * `g_num`: `VARCHAR(10)` (Номер группы хранится как строка, чтобы не терялся ведущий ноль в номерах вида `080255`).

## Пример 3: CRM-система учета клиентов и сделок (B2B CRM)

Описывает компании-клиенты, их контактных лиц и коммерческие сделки. Схема находится в **3НФ**: реквизиты компании-клиента хранятся только в таблице `accounts`, а контакты и сделки ссылаются на неё через внешний ключ `account_id`.

### 1. Таблица `accounts` (Компании-клиенты)
*Первичный ключ:* `account_id`

| account_id (PK) | company_name | industry |
| :--- | :--- | :--- |
| **1** | EPAM Systems | IT |
| **2** | Belinvestbank | Banking |

### 2. Таблица `contacts` (Контактные лица)
*Первичный ключ:* `contact_id` | *Внешний ключ:* `account_id` -> `accounts(account_id)`

| contact_id (PK) | full_name | email | account_id (FK) |
| :--- | :--- | :--- | :--- |
| **10** | Дмитрий Дащинский | dmitry@epam.com | 1 |
| **20** | Иван Гук | ivan@belinvest.by | 2 |

### 3. Таблица `opportunities` (Сделки)
*Первичный ключ:* `opp_id` | *Внешний ключ:* `account_id` -> `accounts(account_id)`

| opp_id (PK) | deal_title | amount | close_date | account_id (FK) |
| :--- | :--- | :--- | :--- | :--- |
| **501** | Cloud Migration | 25000.00 | 2026-12-31 | 1 |
| **502** | Security Audit | 15000.00 | 2026-11-15 | 2 |
